# University Lab & Equipment Booking System

## Context

Hackathon build. The rulebook (`docs/rulebook.md`) specifies a university resource-management app: students/faculty reserve labs and equipment, lab staff approve and issue, coordinators and admins oversee, and the system prevents double-booking while producing usage analytics.

Problem it solves: universities book labs/equipment through paper forms and WhatsApp, causing double bookings, unknown custody, delayed approvals, missing/damaged gear, and no usage data.

Outcome: a deployed Next.js app with real auth, four roles, an approval workflow, DB-enforced conflict prevention, issue/return tracking, and analytics.

**Constraints locked with the user:**
- Supabase (live project), schema applied by pasting migration files into the SQL Editor — Supabase CLI is not installed and `npx supabase` hangs in this environment
- Real Supabase Auth with seeded demo accounts (one per role)
- Intelligent features are **deterministic algorithms**, not LLM
- Student + Lab Staff deep; Coordinator + Admin lean
- Bonus features: QR checkout/return, waitlist, damage image upload, usage heatmap
- 4 hour budget
- Schema must leave room for advanced features later

## Stack facts (verified, not assumed)

Next.js **16.3.8** — read from the bundled docs before writing code, per `AGENTS.md`.

- **Cache Components is opt-in**, not default. `cacheComponents` is absent from `next.config.ts` and must stay absent. Without it the pre-16 caching model applies: Supabase client calls are not `fetch`, so they are not cached. Do **not** reach for `'use cache'`, `cacheLife`, `cacheTag`, `updateTag`, or `<Suspense>`-wrapping for data freshness.
- Mutations are **Server Functions** (`'use server'`). After a mutation call `revalidatePath(...)` or `refresh()` from `next/cache`. `redirect()` from `next/navigation` throws, so call revalidation first.
- `params`, `searchParams`, `cookies()`, `headers()` are **async only**. Use `PageProps<'/route'>` / `LayoutProps<'/'>` / `RouteContext<'/api/x/[id]'>` — globally available, generated by `next dev`/`next build`/`next typegen`.
- `middleware.ts` no longer exists → **`src/proxy.ts`** (sibling of `src/app`), exporting `proxy` or a default. Runtime is nodejs, not edge.
- `next lint` is removed; lint via the ESLint CLI (`npm run lint` already does this).
- Turbopack is the default for both `dev` and `build`. `next dev` writes to `.next/dev`.
- **Server Functions are reachable by direct POST** — every action must re-check auth and role itself. Never rely on the proxy alone.
- `@supabase/ssr` **0.12.7**: the `get`/`set`/`remove` cookie methods are deprecated. Use `getAll`/`setAll`. `setAll` receives `(cookiesToSet, headers)` — those headers must be written to the response to prevent CDN-cached session leakage.
- A new Supabase server client per request, never shared. Call `getClaims()`/`getUser()` early so token refreshes can write cookies.

## Deliverables

### 1. Foundation

`.env.local` (gitignored already): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (seed script only).

- `src/lib/supabase/client.ts` — `createBrowserClient` with the `Database` generic
- `src/lib/supabase/server.ts` — `createServerClient` with `getAll`/`setAll` against `await cookies()`, wrapped in try/catch since Server Components cannot always write cookies
- `src/proxy.ts` — session refresh on every request, redirecting unauthenticated users away from `/(app)`. Optimistic only.
- `src/lib/auth.ts` — `requireUser()` and `requireRole([...])`; both throw/redirect. Called at the top of every page **and every Server Action**.
- `src/lib/types.ts` — hand-written `Database` type matching the migrations (skip `supabase gen types`, which needs the CLI)

### 2. Database

`supabase/migrations/` — real, versioned, CLI-compatible files, also pasteable into the SQL Editor.

- `0001_schema.sql` — enums + tables:
  `departments`, `profiles`, `labs`, `equipment_categories`, `equipment`, `bookings`, `booking_equipment`, `issues`, `booking_rules`, `notifications`, `waitlist`
  - `profiles.role` enum: `student | faculty | lab_staff | coordinator | admin`
  - `labs.status`: `available | reserved | in_use | maintenance | closed`
  - `bookings.approval_status`: `pending | approved | rejected`
  - `bookings.booking_status`: full lifecycle `draft → pending_approval → approved → reserved → in_use → completed`, plus `rejected | cancelled | overdue | returned_late | damaged` — matches the rulebook's status list
  - **`available_quantity` is not stored.** It is computed in a view `equipment_availability` as `total_quantity − reserved − in_use`. Stored counters drift; the rulebook lists it as a field but a derived value is correct and cannot disagree with the bookings table.
  - `waitlist` table ships in the first migration so later advanced features have their slot.
- `0002_rls.sql` — enable RLS on every table. Add `auth_role()` as a `SECURITY DEFINER` function returning the caller's role — policies on `profiles` that query `profiles` recurse infinitely without it.
  - labs/equipment/categories: readable by all authenticated, writable by lab_staff+
  - bookings/waitlist: owner reads and writes own; staff+ read their department
  - issues/notifications: owner reads own; staff+ read/write
  - profiles: own row, staff+ read department, admin reads all
- `0003_conflict_guard.sql` — `CREATE EXTENSION btree_gist` plus an EXCLUDE constraint:
  `EXCLUDE USING gist (lab_id WITH =, tsrange(...) WITH &&) WHERE (booking_status IN ('approved','reserved','in_use'))`
  The database itself makes double-booking impossible, not just the app. Application code pre-checks for good UX; this is the backstop against races.
- `0004_seed_reference.sql` — 4 departments, ~8 labs, ~10 equipment categories, ~25 equipment rows, booking rules, and a spread of historical bookings across past months so the analytics and heatmap are not empty on first load.

Demo users are created by `scripts/seed-users.ts` using the **Supabase Admin API** (`auth.admin.createUser` with the service-role key) — the supported path, far more reliable than inserting into `auth.users` by hand. One account per role, known passwords, printed to console on completion. Non-interactive demo login buttons on the login page for each role.

### 3. Booking engine — `src/lib/booking/`

Pure, unit-testable functions with no Supabase import, so the logic can be exercised without a database.

- `availability.ts` — `overlaps(a, b)`, `findConflicts()`, `findAlternativeSlots()` walking 30-minute increments inside lab open hours, `findAlternativeLabs()`
- `recommend.ts` — **Smart Resource Recommendation**. Scores each candidate lab on capacity fit, facility match, department match, availability, and historical utilization; returns ranked results with a match percentage, mirroring the rulebook's Lab A/B/C table.
- `rules.ts` — enforces max duration, max equipment quantity, advance booking limit, approval-required equipment, department access
- `status.ts` — the legal transition map, plus `assertTransition()` which throws on an illegal move
- `priority.ts` — **Priority Recommendation**. Scores faculty over student, urgency by date, and purpose keywords (exam, thesis, research, deadline) so staff can triage

### 4. Routes

Route group `(app)` holds the authenticated shell (sidebar nav, role badge, notifications bell) in its `layout.tsx`.

- `(auth)/login`, `(auth)/signup` — real Supabase email/password auth; login carries the demo-account buttons
- `(app)/dashboard` — role-aware: student sees upcoming bookings and returns due; staff sees the pending queue; admin sees system stats
- `(app)/labs`, `(app)/labs/[id]` — browse, filter by department/capacity/facility; detail page shows an availability grid
- `(app)/equipment`, `(app)/equipment/[id]` — browse, filter by category, live available quantity from the view
- `(app)/bookings/new` — the request wizard: pick resource → date/time → availability check → rule check → smart alternatives when unavailable → submit. This is the demo centrepiece.
- `(app)/bookings`, `(app)/bookings/[id]` — history and a status timeline
- `(app)/approvals` — staff/coordinator queue with priority badges, approve/reject with reason
- `(app)/issues` — staff desk: issue, return, record condition, damage report with image upload, overdue list
- `(app)/scan` — QR display for an issue; lookup by manual code. Camera scanning via `BarcodeDetector` is Chromium-only and stalls on stage, so manual code entry is the primary path and camera is a progressive enhancement.
- `(app)/waitlist` — join/leave on a fully-booked slot; auto-promote the head of the queue when a booking is cancelled
- `(app)/analytics` — coordinator/admin: totals, approvals, pending, cancelled, equipment out, overdue, most-booked labs, most-used equipment, utilization, damage reports, usage by department, peak hours, underused labs, plus the **usage heatmap** (pure CSS grid over day × hour)
- `(app)/admin` — users, departments, labs, equipment categories

Most mutations are Server Actions in `src/lib/actions/` colocated by domain (`bookings.ts`, `approvals.ts`, `issues.ts`, `waitlist.ts`, `admin.ts`), each starting with a role check.

New components: `app-shell`, `sidebar-nav`, `status-badge`, `booking-card`, `availability-grid`, `stat-card`, `usage-heatmap`, `qr-code` (SVG QR generator — no dependency installed, so either `npm i qrcode` or a small in-repo encoder; adding the dep is the cheaper call), `empty-state`.

## Risks, stated up front

1. **Migration paste is manual.** Four files, four pastes, in order. A failure mid-way leaves a half-built schema; `0001` will be written idempotently where cheap.
2. **The EXCLUDE constraint surfaces raw Postgres errors.** Server Actions must catch the violation and map it to a human message, or a race between pre-check and insert shows the user a database error string.
3. **Seeded analytics depend on `0004` running fully.** If the historical booking seed fails, the heatmap and charts render empty and look broken.
4. **QR camera scanning may not work** on the demo machine. Manual code entry is the fallback and is built first.
5. **Scope.** 3h40m of work against 4h. If the core slips, waitlist and the analytics deep-dive are the first cuts — the booking → approval → issue → return spine is never cut.

## Verification

Run `npm run dev` and walk the spine end to end:

1. Log in as the student demo account. Browse labs, filter, open a lab detail page.
2. Request the same slot twice for one lab — the second attempt must surface a conflict **and** ranked alternative labs with match percentages.
3. Request more equipment units than available — must be refused with the actual available count.
4. Log in as lab staff. The request appears in the approvals queue with a priority badge. Approve it.
5. Issue the equipment from the issues desk. Confirm the QR code renders and the manual code resolves.
6. Return it with a damage report and an uploaded image. Status becomes `damaged`, and the equipment's damage count increments.
7. Force an overdue issue, confirm it appears in the overdue list.
8. Confirm `equipment_availability` reflects the new counts, and that the lab's reserved slot is released on cancellation.
9. Join a waitlist on a fully-booked slot, then cancel someone's booking and confirm the promotion fires and writes a notification row.
10. Open analytics as coordinator/admin — verify heatmap, peak hours, most-booked labs, and damage reports are populated from the seeded history.
11. Attempt a cross-role action directly (a student POSTing an approve action) and confirm it is rejected server-side.
12. `npm run lint` and `npm run build` clean.
